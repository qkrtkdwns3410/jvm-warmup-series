# 1부. 첫 요청이 느린 범인은 JIT 하나가 아니다

> 상태: 초안

## 서론

배포는 끝났다. 헬스 체크도 초록불이고 CPU도 멀쩡하다.

하지만 첫 요청은 800ms가 걸렸고, 같은 요청을 몇 번 보내자 응답 시간은 30ms까지 떨어졌다. 일반적인 운영 환경에서는 배포 직후부터 수많은 요청이 들어오기 때문에 이 차이가 잘 드러나지 않을 수도 있다.

이 현상을 보고 “JVM 워밍업이 덜 됐나 보다”라고 결론 내리기는 쉽다. 그러나 770ms의 차이를 모두 JIT 탓으로 돌리면 진짜 원인을 놓칠 수 있다.

첫 요청이 느린 순간 JVM과 애플리케이션 안에서 무엇이 시작되고, 무엇이 아직 준비되지 않았는지 분해해 보자.

## 첫 요청의 지연에는 세 개의 시계가 있다

“첫 요청이 느리다”는 하나의 현상 안에는 적어도 세 종류의 시간이 섞여 있다.

1. JVM 프로세스가 시작되고 필요한 클래스를 읽는 시간
2. Spring이 Bean과 프록시를 만들고 DB 연결 등을 준비하는 시간
3. JVM이 실제 요청 경로를 실행하며 자주 사용되는 코드를 학습하는 시간

문제는 세 종류의 작업이 비슷한 시점에 발생한다는 것이다. DB 커넥션 생성이 느린데 JIT를 튜닝하거나, 아직 한 번도 실행되지 않은 요청 경로의 초기화 비용을 JIT 문제로 오해할 수 있다.

반대로 서버가 기동 완료됐다는 이유만으로 JIT 최적화까지 끝나 성능도 준비됐다고 생각하는 것 역시 위험하다.

| 구분 | 대표적인 원인 | JIT와의 관계 |
|---|---|---|
| 프로세스 시작 | JVM 실행, 클래스패스 탐색, 초기 클래스 로딩 | 간접적 |
| 애플리케이션 초기화 | Spring Bean·프록시, DB·Redis 연결, 캐시 생성 | 대부분 별개 |
| JVM 워밍업 | 인터프리터 실행, 프로파일 수집, JIT 컴파일 | 이번 시리즈의 핵심 |

JVM 워밍업은 서버가 처음 켜질 때 생기는 모든 문제의 이름이 아니다. 반복 실행되는 코드를 더 빠르게 실행하기 위해 JVM이 런타임 데이터를 수집하고 최적화하는 과정이다.

## 서버가 켜진 것과 성능이 준비된 것은 다르다

```text
프로세스 실행
  → 애플리케이션 초기화
  → readiness 통과
  → 첫 요청
  → 반복 실행
  → 주요 경로의 성능 안정화
```

각 상태는 서로 다른 의미를 가진다.

| 상태 | 의미 |
|---|---|
| Started | JVM 프로세스가 실행됐다. |
| Ready | 애플리케이션이 트래픽을 받을 수 있다고 판단했다. |
| Warmed up | 주요 요청 경로가 반복 실행되어 성능이 안정된 상태에 가까워졌다. |

readiness가 성공했다는 것은 요청을 처리할 수 있다는 뜻이지, 응답 시간이 이미 안정됐다는 뜻은 아니다.

## 첫 요청에 숨어 있을 수 있는 비용

첫 요청에는 다음 비용이 한꺼번에 포함될 수 있다.

- 필요한 클래스의 로딩과 초기화
- 지연 생성되는 Spring Bean과 프록시의 첫 사용
- 리플렉션, 직렬화기와 검증기의 초기화
- DB 커넥션 풀의 첫 연결
- DNS 조회와 TCP·TLS 연결
- 애플리케이션 또는 외부 캐시의 미스
- 인터프리터 실행과 JIT 컴파일
- OS 페이지 캐시와 CPU 캐시의 차이

따라서 첫 요청의 770ms는 하나의 비용이 아니라, 아직 실행되지 않았던 여러 작업의 합계일 가능성이 높다.

## 응답 시간의 모양으로 세운 첫 번째 가설

아래 수치는 흐름을 설명하기 위한 가상의 예시다.

```text
서버 시작 직후 첫 요청  800ms
두 번째 요청           220ms
10번째 요청             55ms
100번째 요청            30ms
```

- 첫 요청에서만 시간이 크게 튄다면 연결이나 일회성 초기화 비용을 의심할 수 있다.
- 여러 요청에 걸쳐 서서히 감소한다면 런타임 프로파일 수집과 JIT의 영향을 의심할 수 있다.
- 특정 API에서만 반복된다면 해당 요청 경로의 클래스 로딩, 외부 연결 또는 캐시를 살펴봐야 한다.

이것만으로 원인을 확정할 수는 없다. 다만 “느리다”를 관찰 가능한 패턴으로 바꾸면 무엇을 측정해야 하는지가 보이기 시작한다.

## 정리

서버가 켜졌다는 것과 서버의 성능이 준비됐다는 것은 다르다. 첫 요청의 지연을 분석하려면 애플리케이션 초기화 비용과 JVM 워밍업 비용부터 분리해야 한다.

다음 편에서는 Java 코드가 처음부터 최적화된 기계어로 실행되는 것이 아니라, 인터프리터와 JIT 컴파일러를 거치며 변해가는 과정을 살펴본다.
